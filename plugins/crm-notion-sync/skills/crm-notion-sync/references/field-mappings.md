# Field Mappings

Read this before Job 2 or the picklist drift check in Maintenance Check.

## Technical Sales Process fields (synced via Job 2, Notion → SF)

| Notion property | Type | Salesforce field |
|---|---|---|
| SA Next Steps | Text | `POV_Notes_Summary__c` |
| POV Health | Select: Green, Yellow, Red | `POV_Health__c` |
| Tech Validation Type | Select: Discussion-Based Evaluation, Hands-on POV, Partner-Led POV, No SA Involved in Opportunity | `Technical_Validation_Type__c` |
| OK for Tech Validation | Checkbox | `OK_for_Tech_Validation__c` |
| Technical Validation Start Date | Date | `POV_Start_Date__c` |
| Technical Validation End Date | Date | `POV_End_Date__c` |
| Tech Win? | Checkbox | `Technical_Win__c` |
| Technical Win Date | Date | `Technical_Win_Date__c` |
| Technical Sales Retro | Text | `Technical_Sales_Retro__c` |
| Deployment Type | Select: Single Tenant, Multi Tenant | `Deployment_Type__c` |
| Deployment SKU | Select (see SKU note below) | `Deployment_SKU__c` |
| POV Engine | Select: Core, Fusion | `POV_Engine__c` |
| Deployment Engine | Select: Core, Fusion | `Deployment_Engine__c` |
| (your org's equivalent of churn-risk flag) | Checkbox | `{churn_risk_field}` from settings (`salesforce.churn_risk_field`) — confirmed by the SA during setup, since some orgs have two similarly-named fields; don't guess which one is "yours". If it's `null`, skip this field. |

**Field naming traps to watch for** (confirmed to exist in at least one dbt
Labs org — check your own before assuming):
- `POV_Engine__c` ("engine used during technical validation") vs.
  `Deployment_Engine__c` ("engine used in the live/production deployment").
  Same picklist values (Core, Fusion), different meaning. Each maps to its
  own Notion field — never write one's value to the other.
- A personal "contraction/churn risk" field that's yours vs. a
  similarly-labeled org-wide field that isn't. Confirm the exact API name
  with whoever owns your Salesforce schema before the first Job 2 run.

## Not synced by design (typical pattern — confirm your org's equivalents)

- A next-steps *date* field that's auto-set by Job 2 whenever the next-steps
  text changes — this is "date the note was taken," not "expected completion
  date." If your org wants to track expected completion separately, that's a
  different field and needs its own mapping — don't conflate the two.
- An append-only history/log field, auto-generated by Job 2, never
  hand-edited in Notion.
- A POV/scoping document link field, populated from the Notion page URL
  (handled by Maintenance Check's POV link check, not Job 2).
- Fields explicitly marked "not my responsibility" by the SA (e.g. deployment
  cloud provider, manager-only forecast notes) — stored in `excluded_fields`
  on the settings page and confirmed with the user during first-time setup;
  don't assume one SA's exclusions apply to someone else's book.
- A constant "technical lead" field that's always the SA on their own opps —
  not worth tracking as a variable field.

## Deployment SKU comma/dash translation

Notion select options can't contain commas (hard platform limit). Any
Salesforce picklist value containing a comma needs a dash substitute in
Notion. In one dbt Labs org these four values needed translation — your org's
list may differ, so verify against your own SF picklist via `describe_object`
rather than assuming this list is complete:

| Salesforce (comma) | Notion (dash) |
|---|---|
| dbt Cloud Azure Multi Tenant, Ireland | dbt Cloud Azure Multi Tenant - Ireland |
| dbt Cloud Azure Multi Tenant, United States | dbt Cloud Azure Multi Tenant - United States |
| dbt Cloud GCP Multi Tenant, England | dbt Cloud GCP Multi Tenant - England |
| dbt Cloud GCP Multi Tenant, United States | dbt Cloud GCP Multi Tenant - United States |

Writing to Salesforce (Job 2): translate dash → comma for these values first.
Reading from Salesforce (Job 1 or the picklist drift check): translate
comma → dash before writing to Notion. All other values are identical in
both systems.

## Customer Journey logic (Full Sync only, not standalone Job 1)

Reflects where the account sits in the overall relationship — **not** the
Salesforce opportunity StageName. Source: all opportunities for the account
(open and closed), with Job 1's Cancel-type and owner-mismatch exclusions
applied to determine which opps count as "open."

Evaluate in order, use the first rule that matches:
1. **Land Opportunity** — at least one open (post-exclusion) Land-type opp.
2. **Expansion / Renewal Opp** — at least one open Renew or Expand opp, and
   no open Land opp.
3. **Onboarding** — a recent Closed Won Land opp (within ~6 months) and no
   open opps.
4. **Target Prospect (pre-opp)** — no open opps and no Closed Won history.
5. **Inactive** — no open opps, no Closed Won history, all opps Closed Lost.
6. If none of these fit cleanly: flag for the user rather than guessing.

## How to read the three ARR columns together

| Current ARR | Next Opp Delta ARR | Largest Delta ARR | What it means |
|---|---|---|---|
| High | $0 | $0 | 🚨 Big customer at risk — no active opp, check in |
| Low | $0 | $0 | 👀 Monitor but lower priority |
| $0 | High | Same | 🟡 New logo, solid upside, push forward |
| High | Positive | Bigger | ✅ Healthy customer — expand opp bigger than renew |
| Moderate | $0 | $0 | 📋 Flat renewal — manage efficiently |
